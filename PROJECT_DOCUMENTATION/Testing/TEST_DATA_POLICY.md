# SporeKart Test Data Policy

**Version:** 1.0
**Owner:** QA Lead
**Status:** Approved
**Classification:** Mandatory — All QA Programs

---

## 1. Policy Statement

The Enterprise QA Program MUST execute entirely in **Mock / QA mode**. No QA test may connect to, read from, write to, or depend on any production resource.

This policy is **mandatory and non-negotiable**. Violations must be reported as P0/Security incidents.

---

## 2. Prohibited Connections

| Resource | Prohibited | Allowed |
|---|---|---|
| Production Database | ❌ | QA Database (isolated) |
| Production Secrets | ❌ | QA-specific mock secrets |
| Production APIs | ❌ | Mock API endpoints |
| Live Payments | ❌ | Payment gateway sandbox / mock |
| Live Shipping | ❌ | Shipping provider sandbox / mock |
| Live Email | ❌ | Mailtrap / mock SMTP |
| Live SMS | ❌ | Mock SMS provider |
| Live WhatsApp | ❌ | Mock WhatsApp provider |
| Production Storage | ❌ | QA storage bucket (isolated) |
| Production Analytics | ❌ | QA analytics endpoint (isolated) |
| Real Customer Information | ❌ | Synthetic / anonymized test data |

---

## 3. Environment Definitions

| Environment | Purpose | Data Source | Connected To |
|---|---|---|---|
| **Development** | Local coding, unit tests | Local seed data | Local mock services |
| **QA** | Test execution, regression | Synthetic seed data | QA-isolated services |
| **Staging** | Pre-production validation | Anonymized subset | Staging services |
| **Production** | Live customer traffic | Real customer data | Production services |

**QA and Development environments MUST NEVER have network access to Production.**

---

## 4. QA Data Reset Policy

- QA database is reset to a known seed state at the start of every QA sprint.
- QA database is reset after every regression pass.
- QA database is reset after any destructive test (delete, update, bulk write).
- Reset is automated via a seed script stored in `testing/seed-data/`.
- Reset must complete in under 5 minutes.

---

## 5. Seed Data Policy

- Seed data is synthetic — no real customer information.
- Seed data covers all feature areas under test.
- Seed data is version-controlled in the repository under `testing/seed-data/`.
- Seed data is reviewed and updated per sprint.
- Seed data must be reproducible (deterministic).

---

## 6. Synthetic Test Data Policy

- All test data must be generated by a script — never copied from production.
- Synthetic data must include edge cases: empty, null, boundary, invalid, malicious.
- PII-like fields (name, email, phone) must use placeholder values (`test-user-N@sporekart-qa.com`).
- Payment data must use provider sandbox card numbers.
- Shipping addresses must use QA facility addresses.

---

## 7. Data Reset Procedure

1. Run `testing/scripts/reset-qa-db.sh` (or equivalent).
2. Run `testing/scripts/seed-qa-data.sh`.
3. Verify seed count matches expected.
4. Log reset timestamp in QA sprint report.

---

## 8. Violation Handling

Any violation of this policy (e.g., a test connecting to production) is:
- Immediately escalated to Security Lead.
- Treated as a P0/Security incident.
- Root cause documented in `PROJECT_DOCUMENTATION/Security/`.
- Corrective action applied before QA resumes.
